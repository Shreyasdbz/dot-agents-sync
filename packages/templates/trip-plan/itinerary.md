# Itinerary composition guide

Create a plan grounded in actual traveler constraints. Choose only the relevant modules; a day trip should not look like an international relocation dossier.

## Quick glance

Dates with local zones, travelers and accessibility/dietary constraints, route, pace, fixed commitments, budget currency/basis and current planning status. Distinguish booked, candidate and unresolved items. Exclude sensitive booking/contact identifiers from a shareable version.

## Choose the structure

- **Day trip:** arrival/departure bounds → timed route → meals/breaks → weather alternative → estimated costs and open checks.
- **Single base:** accommodation area → daily clusters → transit options → flexible/rest blocks → budget.
- **Multi-city:** flight/rail legs with local dates/zones → transfer buffers → day clusters → luggage/check-in constraints → cost basis.
- **Group or accessibility-led:** shared fixed commitments → optional branches → step-free/rest/dietary constraints → decision owner if supplied. Never infer a traveler's medical needs.

## Day module

Use **local date and zone / intended outcome / fixed anchors / flexible stops / transit and buffers / food and rest / fallback**. For each stop, retain time window, duration, status, source/check date and feasibility constraints when known. Missing opening hours are not confirmed availability. Avoid impossible connections and unexplained teleportation between cities.

## Logistics and cost modules

Load [modules.md](modules.md) for flight/rail legs, cost breakdowns and source records. A total must state currency, per-person/party basis, inclusions, exclusions and whether it is quoted, estimated or paid. Do not sum different currencies or count a shared booking once per traveler.

## Finish

List material unresolved decisions, checks needed before booking, and the evidence freshness. A local itinerary is not a reservation. For public HTML, use the Trip Publish components and carry forward the same status and uncertainty.
