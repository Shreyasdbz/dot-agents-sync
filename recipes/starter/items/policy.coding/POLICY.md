# Coding quality

Follow observed repository conventions and language idioms. Prefer the smallest coherent implementation that meets the contract. Keep errors actionable, validate boundary inputs, and remove unreachable scaffolding. Split mechanical transformations from behavioral changes where that aids review.

Allow local duplication when extracting it adds more coupling than value. Do not independently duplicate shared types, API contracts or external-call logic; give those boundaries one authoritative schema or focused client. Avoid speculative scaling, extension frameworks and unsupported edge cases without observed or explicitly planned requirements. Reachable invalid inputs, security boundaries and data-loss risks remain in scope regardless of project size.

Give components and modules one cohesive responsibility and a clear reason to change; separate presentation, orchestration and external effects where that improves comprehension. Keep state near its owner and avoid redundant synchronized state. Do not split files merely to meet a line count. Minimal footprint means low maintenance burden, not compressed code.

Document public functions, classes, types and interfaces with concise contract comments or docstrings: semantics, invariants, units, side effects and failure behavior where relevant. Do not repeat names or signatures in prose. Explain why consequential branches or non-obvious operations exist and what breaks without them. Preserve language conventions and generated/vendor code boundaries.

Before calling implementation done, inspect the final diff and affected boundaries for speculative abstractions, redundant wrappers, harmful duplication, unused code, unnecessary dependencies, swallowed errors, misleading fallbacks, stale comments and filler text. Fix in-scope findings and verify changed behavior; report remaining blockers or verification gaps. This audit is required even without a specialist agent, but does not authorize delegation or unrelated cleanup. Static checks and self-review do not prove independent review or production behavior.

Track concrete out-of-scope findings for a separate cleanup PR under the selected planning policy; do not silently ignore them or expand the current diff. Check for an existing item before creating one. In GitHub, use Bug for an observed defect, Task for maintenance, and the relevant native Feature as direct parent for feature Tasks; do not invent a Feature for standalone cleanup. Include evidence, impact and a bounded acceptance check. Use authorized tracker operations; when access or write approval is absent, provide a ready-to-file item and explicitly report it as unpublished. A finding that blocks safe completion must be raised now, not hidden in future cleanup.
