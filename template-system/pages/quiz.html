What survives a failed invoice write?

Under the new transaction, what does the retry encounter?

Why each option is right or wrong

  1. Incorrect · the old failure mode

    A separately committed event key could survive the invoice error before this change. In the new transaction it rolls back too, so it cannot suppress this retry.

  2. Correct · shared rollback

    The event key and invoice share one commit boundary. The error happens before that commit and rollback succeeds, leaving neither row durable. The retry can reattempt the transaction; success is not guaranteed.

  3. Incorrect · assumed completion

    Both rows become durable only after a successful commit. The specified error occurs earlier, so there is no stored invoice to return.

  4. Incorrect · partial persistence

    The shared rollback prevents either inserted row surviving alone. An invoice-only result contradicts the given transaction boundary and successful rollback.

Which rows are durable when the sender retries?

Why each option is right or wrong

  1. Correct · an independent commit

    The key survives because its commit already completed. In this historical contract it suppresses the retry even though the invoice failed.

  2. Incorrect · assumed shared rollback

    The invoice failure cannot roll back the earlier separate event-key commit.

  3. Incorrect · assumed successful write

    The invoice attempt failed and no invoice existed before it. Only the key is durable.

  4. Incorrect · reversed persistence

    The event key committed; the invoice failed. This option reverses which operation reached durable state.
