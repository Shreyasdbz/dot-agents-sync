# Authoring and refreshing project context

Private context packages describe what an authorized source should contain; they do not supply real project facts. Provider output contains a gated lookup, not the private contract or source bytes. Read the relevant catalog contract when authoring a source. The dasync CLI distributes selections and resolves approved bindings; it does not generate or refresh project knowledge automatically.

During authorized project work, draft context from inspected repository evidence and ask only about material gaps or conflicts. Use existing approved source locations. If none exists, propose a location and privacy scope; do not create a binding, scan unrelated personal files or expand consumer/provider grants. Personal music and travel preferences stay private; optional public presets express reusable guidance without asserting facts about every adopting project.

Keep the document small: applicable scope, current facts, intended changes, constraints, unresolved questions and supporting references. Omit irrelevant sections. For material claims include source paths or approved document references, verification date/revision and evidence class: observed, intended, inferred or unknown. A configuration setting is not proof of a successful deployment or runtime behavior.

Use maintained code and configuration for current implementation; use approved design/product decisions for intended direction. Surface conflicts without silently discarding either source. Product goals, users and success measures cannot be inferred reliably from code. Preserve human-authored decisions and annotate what remains unresolved.

Refresh only affected claims when related authorized changes invalidate them. Reinspect the relevant evidence, preserve unrelated content and mention consequential revisions. If the source is inaccessible or outside the write scope, flag staleness and propose an update. Do not create a background monitor, refresh timestamps without verification or rewrite all context after every edit.

Repository architecture should describe a few important flows and ownership boundaries. Conventions distinguish enforced rules from examples. Stack context separates declared, resolved and tested versions. Product context distinguishes research, decisions and hypotheses. Private preference overrides contain genuine exceptions rather than copies of the general policy.

Validate the source for secrets, unsupported assertions, broken references, repetition and stale claims before binding it. Test binding and materialization behavior in temporary environments. Actual project context remains private by default; installation, publication and tracker mutation are separate actions with separate authority.
