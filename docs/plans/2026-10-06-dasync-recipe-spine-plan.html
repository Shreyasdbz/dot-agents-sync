01Decisions and delivery boundary

dasync becomes the engine; independently maintained recipe repositories and individual local items supply content. One canonical format serves authors. The engine translates it into provider-native output and exposes the same operations through a human CLI, a polished TUI, and a versioned machine interface.

Settled with the userEffect on the design
Individuals and teams at first public launchGit/private sources, local items, composition, author tooling, recovery, and the TUI are launch gates—not distant ecosystem aspirations.
Provider-neutral authorshipRecipes contain canonical content and essential semantics. Adapters own native formats. Authors do not maintain Claude/Codex/etc. variants.
No profilesRecipes and individual items are the selection model. No presets, bundles, default-item groups, or hidden profile replacement.
Small development starter, default yesOnboarding offers the starter, another approved source, or none. It selects current items only; trust and additional approvals remain distinct.
Same names may coexistIdentity includes the source. Names never imply override priority or install-order precedence.
Explicit cross-recipe dependenciesSupported at first stable launch. Sources and pins are deliberate; no silent substitution or source fetch triggered by recipe prose.

Compose personal and project selections by defaultResolve both with explicit conflict checks. Team locks remain project-owned. Private contexts and hooks keep separate gates.
No backward compatibility requirementDesign a clean protocol. Existing user files still need protection; format reset does not authorize destructive migration.
HTML onlyOne offline document, including an embedded validated Plan Context; no external publication or separate delivered JSON file.
Status: design reviewed through independent evidence gathering and two scrutiny rounds; implementation is proposed. Synthetic contract probes and document checks are recorded in Validation evidence. They do not certify the future engine, native host discovery, or model behavior.

This is an unpublished planning projection of the existing GitHub authority. Live issue, milestone, field, and workflow refresh could not be completed through the available shell network. No tracker IDs, assignments, dates, estimates, or completion statuses are invented. All implementation work below is proposed.

Recipe authors should spend their effort on content, references, and examples. A first useful item should not require a package registry account, a hosted service, a provider-specific build system, a model API key, or knowledge of every adapter. Team and community maintainers can add review discipline without creating another content format.

Content ownership, protocol ownership, and adapter ownership have different reasons to change. A poor Harmonic architecture reference is a recipe issue; a correctly declared role losing an essential restriction during translation is an adapter issue; nondeterministic selection or broken rollback is a spine issue. Diagnostics and contributor documentation must route those reports accordingly.

The observed current catalog contains 65 packages. The current renderer already rejects output collisions. The gap is that flattening dots into hyphens can reject legitimate distinct IDs; this is not evidence of silent overwriting. Likewise, installed executables and rendered files are not evidence that a provider or model exercised a workflow.

04Ownership and the installation pipeline

Content owners

Starter recipe · community recipes · private team recipes · local individual items

Canonical content, declared files, item metadata, references, provenance, and examples.

Spine

Source preparation → validation → composition → plan → apply → receipt / recovery

Protocol, schemas, adapters, authority checks, durable state, CLI / TUI / machine interface.

Provider boundary

Native files and supported semantics → documented or observed host discovery → model workflows

Each step has its own evidence. The spine does not become an agent runtime.

Implement cohesive application functions around the existing Engine. The CLI, TUI, and machine mode call those functions with the same typed requests; they do not independently resolve graphs or write provider files. Source preparation has a separate effect boundary because it contacts networks and populates immutable caches without selecting or activating content.

The spine repository owns its synthetic fixtures, conformance kit, schema reference, and examples. Recipe-specific generated templates, content tests, and behavioral evaluation cases follow the recipe that owns them. The engine test suite must be usable when the official starter origin is unavailable.

05Identity, origins, aliases, and native names

Use a stable source UUID for each recipe or standalone local-item source. A recipe-local item ID identifies kind and responsibility. The authoritative item key is the structured pair (source UUID, local item ID). Display aliases such as harmonic/skill.pr-review are selectors, not authentication or precedence.

ConceptPurposeChange rule
Source UUIDContinuity of a content collection or singleton local itemForking creates a new UUID. Copying the UUID does not copy trust.
Approved origin + root + transport + registration generationWhere trusted bytes may be retrievedOrigin/root changes need a dedicated provenance review; UUID equality alone cannot authorize relocation.
AliasReadable CLI/TUI selectionRename changes labels only. Ambiguous bare selectors show candidates; no implicit winner.
Snapshot pinExact content used by the environmentOne immutable snapshot per source UUID in one effective environment.
Item versionDependency/contract compatibilityCheck constraints against the selected snapshot; do not infer byte identity from version text.
Native invocation/path mappingDistinct valid provider outputDeterministic stable-key mapping, adapter limits, collision checks, reviewed naming-version migration.

Native names use a bounded readable component plus a fixed digest of the authoritative key. Recipe alias, registration order, and display-name edits do not determine identity. Exact, casefolded, file/directory, reserved-name, character, and length checks run before a plan can apply. A digest collision is an error; no ordinal suffix or last-writer winner silently changes names. Mapping versions and assignments live in machine installation records and receipts, not the portable source lock.

Same-named items from different recipes coexist. Two revisions of the same source UUID do not coexist in one effective graph. A user aligns pins, stops inheriting that source, or intentionally forks under a new identity. Disabling inheritance only changes dasync composition; globally materialized provider content may remain discoverable. Diagnostics must show that separate fact.

06Selection without profiles

Registered sources are available to browse. Root selections express user intent. Dependencies are derived. The resolved graph records direct, inherited, and dependency reasons separately; materialization and observed host visibility are separate states.

  • Selecting a recipe is a bulk UI action over its currently pinned item IDs. It writes explicit roots, not an ongoing subscription to all future items.
  • New items in an updated recipe appear in the update review as available and unselected. Modified selected items and changed dependency closures still appear in the plan.
  • Removing a root removes that selection reason. A dependency needed by another root remains. Explicitly disabling a required item produces a bounded causal blocker.
  • Personal user selections compose with project selections by default when scope/access/capability rules permit. Hooks and private contexts never acquire project/provider grants through inheritance.
  • Same-named context selections do not imply substitution into a workflow. The workflow’s explicit dependency or slot binding decides which content it receives.
  • Selecting two declared conflicting policies fails. Conflict domains are recipe-local unless an explicit shared conflict contract is declared. The engine does not detect all contradictions in natural language.
  • Unregistering an in-use source refuses and shows dependent roots. A reviewed removal may deselect those roots; it never rewrites publisher-authored dependency declarations.
  • Machine-wide unregister cannot silently affect other projects. The initial implementation may unregister only unused sources; multi-scope removal must explicitly enumerate and authorize each scope.

There are no authored selection groups, hidden default-item lists, or profile aliases. A small starter recipe is small by its actual contents. Supporting templates/policies/references are installed through ordinary dependency closure and remain explainable in the same item model.

A checkbox must not convert a derived selection into a direct choice merely because it is visible. The TUI edits intent and keeps its draft separate from persisted configuration. Search, navigation, resize, and inspection have no selection effects.

07Canonical format and future stability

Recommend strict YAML authored documents with JSON-equivalent semantics and bundled JSON Schema 2020-12 validation. Reject duplicate keys, aliases, unsafe tags, unknown core fields, and remote schema resolution. A single authoritative ItemSpec schema is reused by recipe items and local item envelopes; provider frontmatter is generated, not independently authored.

ContractVersion independentlyCompatibility rule
Recipe and ItemSpecAuthored content semanticsFreeze core behavior before stable launch. Unknown required features fail before writes.
Intent and portable lockSelection and resolution semanticsExplicit migrations; local grants cannot be encoded as portable authority.
Machine protocolCommand inputs, outputs, errors, event channelsPermanent discovery bootstrap advertises supported versions; old agents get actionable version refusal.
PlanLocal reviewed execution artifactBind exact versions/inputs; version changes invalidate and require replan.
State / receipt / journalRecovery and historical interpretationBack up state before migrations; unknown formats fail safely; support obligations apply to published generations.
Adapter / name mappingNative translation and semantic preservationSource pins stay portable; output/name transitions require reviewed materialization migration.

Keep PEP 440 item versions and constraint syntax, deliberately reusing the current Python packaging implementation. Document the grammar rather than calling it SemVer. Publisher release labels are not a solver: the commit/tree and digest pin bytes; item versions validate contracts within that selected snapshot. SemVer principles can guide the engine’s public API promises only when that public API is explicitly defined.

Permit namespaced annotation-only extensions inside one bounded extensions field. They cannot alter dependency, access, execution, identity, or rendering semantics. Semantic additions require understood feature gates and conformance fixtures. Do not turn extensions into a second plugin runtime or expression language.

The stable-spec process requires a written change rationale, valid/invalid fixtures, reference implementation evidence, an author-facing upgrade note, and a support/migration decision. Publish only compatibility windows maintainers can staff. No indefinite backport promise or automatic reinterpretation of old security semantics.

Normative schemas are an immediate implementation deliverable. Examples below are concrete design examples; they are not commands or formats supported by the current CLI. JSON Schema’s dialect/vocabulary model informs offline version negotiation. SemVer informs explicit API stability, not the selected PEP 440 parser.

The manifest supplies name, description, entrypoint, version, and declared files once. Canonical bodies can be ordinary Markdown without native frontmatter. Kind-specific metadata must stay small and meaningful; semantic checks sit beside schema validation instead of hiding in a prose convention. Resource budgets apply to files, snapshot totals, graph depth, rendering, and disclosure—not only approximate per-package token counts.

Use finite typed references: canonical Markdown destinations dasync:dependency/<item-reference> and dasync:slot/<slot-name>, plus declared typed invocation fields. The renderer translates those references through the qualified graph. Plain prose and fenced examples are literal. No blanket replacements, expression evaluation, recursive templates, or automatic web dereferencing. Default prompts contain task text; the adapter supplies the correct self-invocation name.

09Cross-recipe dependencies and bounded resolution

Within a recipe, bare item references resolve locally. A declared import gives another source a local author-facing key, but it does not authorize registration, fetching, or trust. The environment supplies the approved origin and chosen immutable snapshot for that source UUID.

Resolve one snapshot per source UUID. Check selected item versions against all incoming constraints. Do not search arbitrary historical package releases or silently advance another recipe to make a graph fit. On conflict, report the affected roots, requirement edges, current pins, and the source whose revision needs a deliberate decision.

CaseResolution behavior
Missing imported sourceShow SOURCE_UNBOUND and the declared UUID/import; offer explicit preparation/registration, with no guessed origin.
Registered source but missing itemShow exact source/snapshot/item and dependent roots; do not use another same-named item.
Conflicting version requirementsReject the combined plan; leave current installation intact. Propose bounded choices, never choose new authority.
Cycle across recipesReturn a short cycle path with qualified identities; no recursive rendering.
Optional suggestionShow as available; no implicit root, dependency, grant, or capability.
Explicit disable of required dependencyExplain reverse dependents; user removes affected roots or cancels.
Unused imported sourceDo not fetch merely because it appears in author metadata.

Keep dependency resolution separate from context binding. A fixed dependency selects a specific item. A slot asks for one explicitly bound compatible context. Arbitrary user substitution of any dependency is deferred; it adds a broad override system before a demonstrated need. A proposed source URL or import declaration is data to inspect, not permission to contact a service.

Two coworkers with different personal selections must retain identical project-owned intent and locks. Their machine-effective plans differ transparently. A project dependency on a personal-only or unresolved local source is marked nonportable. Sharing requires promotion, an approved portable locator, or an explicit unresolved binding that fails with SOURCE_UNBOUND until supplied.

Personal and project selections compose by default. The same source at incompatible pins fails before rendering; stopping inheritance is explicit per source or for the environment. Same-key/same-pin items deduplicate in the resolved graph. Native global/project discovery overlap is reported independently because the engine cannot assert one universal provider precedence.

An explicit machine-owned audience policy—local, team, or public—controls which classified source/item metadata may enter a project lock or export. The stricter of publisher classification and local policy wins. Offline software cannot prove that a remote repository is private; the operator owns actual publication visibility. Classifying a private source as shareable needs a separate reviewed decision.

Redacted support exports are diagnostic-only, clearly non-installable. They redact classified IDs, topology, filenames, digests and origins as well as paths. They never guess a source from a UUID or display name. Generated source locks are reviewable resolution records; update and migration own changes instead of silently rewriting manual edits.

11Source preparation, authentication, and survival

Initial transport scope: HTTPS Git, explicit local Git snapshots, local directory recipes, and local item folders. SSH support requires its own authentication, quoting, and transport acceptance before becoming a claim. Git host neutrality is a protocol goal; enterprise credential-helper/proxy/TLS configurations need documented and tested support rather than implicit acceptance of every Git setting.

  1. Name the candidate. User selects an exact locator, recipe root, and tracking ref or full revision.
  2. Prepare explicitly. Contact only permitted endpoints; populate an immutable staging cache. No selection, durable registration, or trust is saved.
  3. Validate identity and files. Parse bounded metadata, check source UUID/root/declared files, resolve full commit/tree and digest.
  4. Inspect an ephemeral draft. Browse items, imports, sensitivity, capabilities and proposed output. Authentication failures preserve the draft.
  5. Review one concrete plan. Origin trust, executable digests, context grants, classification changes, and overwrites have separate choices.
  6. Apply through Engine. Commit exact durable intent/lock/registration/output state and receipt. Report actual effects and activation evidence.

A branch or release tag is an update preference. Execution uses the resolved immutable commit plus declared-content digest. Sync and apply do not fetch. Updating one source prepares a candidate, validates the complete resulting graph, holds other pins fixed, and applies one reviewed environment transaction. Mutable or unavailable origins leave the last installed snapshot usable where retained bytes suffice.

Centralize restricted Git invocation. Read managed objects with replacement objects disabled. Do not load source-owned hooks/helpers/config/filters, submodules, LFS, or arbitrary executable installation steps. Do not fetch inside a user's local source checkout. Local object import uses a managed reading boundary and leaves the source untouched.

Explicitly filter transport configuration and environment. Allow vetted user credential-helper inputs, locale, executable lookup, TLS trust, and explicit enterprise settings; reject source-owned settings and uncontrolled GIT_CONFIG_*, GIT_DIR, GIT_WORK_TREE, GIT_NAMESPACE, SSH command overrides, URL rewriting, and injected headers. Disable redirect following; a redirect requires explicit registration of the new endpoint before contacting it or passing credentials. Integration tests must prove this policy with the actual Git interface.

Retain complete validated metadata and required content for active locks and retained receipts independently of disposable download caches. Eviction cannot silently break active offline sync or promised rollback. Quotas, tree limits, timeouts, permission errors and interrupted preparation get distinct diagnostics. Purge serializes with preparation/apply/recovery, reports lost recovery capability, and does not claim physical erasure or revocation of downloaded copies.

Git configuration is part of the execution boundary, not just a URL concern. Git bundles are a later offline-transfer mechanism. GitHub immutable releases can strengthen official releases where available; ordinary tags are not assumed immutable.

12Contexts, slots, access, and progressive loading

Context distribution and context use are distinct. Public references may be materialized when permitted. Team/private bytes live in retained private source storage or externally bound local files; generated provider output carries an authorized lookup rather than copying private bodies, linked assets, or paths. Credentials are not context content.

Slot fieldMeaning
Local nameA workflow-owned input, such as workspace
Required / optionalMissing required input blocks; absent optional input is explicitly visible
CardinalityOne context at launch; no implicit merge or precedence
Accepted contract UUID and version constraintExplicit structural compatibility with an imported/local context contract
Content formatMarkdown initially; optional structured validation only where declared and supported
Binding ownerProject/user intent binds qualified consumer#slot to qualified context
Validation evidenceContract/version/format checks; not proof of factual truth or semantic sufficiency

A reusable context contract does not enumerate every future external consumer. Local grants authorize actual selected consumers with a binding/dependency edge; author declarations may narrow access but cannot broaden those grants. Project grants bind the machine-registered project and canonical target, not merely a copyable YAML project name.

The lookup/read protocol reports exact qualified identity, snapshot, declared evidence dates, freshness status, missing-grant state, and bounded references. Public metadata lookup is separate from an explicit private read/locate request. Generated private snippets contain the exact consumer, scope, and item identity—no unresolved consumer placeholder. Selecting another same-named context never repairs a missing binding automatically.

A compact index lets an agent discover relevant references without loading every body. Content is loaded task by task. Parent/child and resumed-agent handoffs carry environment identity, pins, permitted actions, authorized references and unresolved facts; they exclude private bodies by default and recheck grants and decision-critical inputs. The CLI's declared consumer/provider strings are routing checks, not authenticated caller identity.

Sensitivity covers metadata, all declared files, and validated reference closure. A public template cannot declassify a private dependency. A private-to-public update requires an explicit classification review. Arbitrary prose and disguised files cannot be proven harmless by a link validator; documentation must bound the claim. Same-user processes able to read the clone/cache are outside the secrecy guarantee. Repository access revocation cannot revoke downloaded bytes.

13Provider portability without false equivalence

Authors supply canonical instructions, references, and essential versus optional requirements. Adapters own native serialization, applicability, role registration, invocation naming, hooks and supporting references. A format translation is successful only when required semantics are preserved—or the operation stops with a clear incompatibility.

Evidence/stateCan establishCannot establish alone
Format supportedAdapter understands this item and its required canonical semanticsHost configuration currently enforces a restriction
Executable detectedA provider executable is on the inspected pathAuthentication, services, discovery, or model behavior
MaterializedExpected output was written and verified against the reviewed planHost loaded every file or ran the intended role
Host discovery observedAn exact host/version/platform discovered an item in a recorded sessionEquivalent behavior on all hosts or models
Workflow exercisedAn observable outcome was tested at exact revisions with stated tools/grantsUniversal reliability, security isolation, or future-version certification

For agents, separate normative role instructions, essential host restrictions, optional preferences and permitted degradations. A read-only requirement cannot become mere prose while being called enforced read-only execution. If current host configuration disables a documented native restriction, essential enforcement remains blocked/unverified. Unsupported optional semantics may proceed only with disclosed, accepted degradation.

The current spine has Codex, Claude, Copilot and Cursor adapters. Mentioning ChatGPT does not create an adapter or establish filesystem integration there. Qualify actual launch providers/platforms with dated evidence, document unsupported/degraded cases, and use the same adapter contract for future hosts. Mac/Linux are the existing release-testing baseline; Windows support requires its own path, locking, terminal, recovery and executable lifecycle gates.

Aggregate policy and hook files need contributor-level provenance: one file may represent several qualified items. Output ownership remains one authoritative installation owner per concrete path, with all contributing items visible. Adapter/name migrations compare old/new outputs, preserve originals, and keep receipt restoration interpretable within the published support contract.

14Human CLI and first-time onboarding

Human CLI output should show useful tables, concise diffs, exact scope/source/pin, selection reasons, and actionable errors. Raw JSON is machine mode, not the default explanation. Nested help must expose valid options for each purpose. Every essential TUI action has a complete CLI equivalent, including source preparation, local creation, grants, diagnostics, cancellation and recovery.

Onboarding starts with project materialization while composing permitted personal selections. It shows detected providers as detection only, names the target, and offers the small official starter with a default-yes selection. Custom source and skip are equally visible. The final plan can collect distinct source trust, exact executable approval, context grant, classification and overwrite decisions on one screen; ordinary confirmation cannot supply omitted categories.

Fetching is explicit and progress is meaningful without unmeasured completion percentages. Cancellation before apply discards draft durable intent but may retain documented cache. Authentication or network failure retains choices and the installed snapshot. Existing files receive drift/collision diagnostics; no generic overwrite recommendation dismisses a real ownership conflict.

16AI-friendly operation as a public API
Freeze a tiny permanent bootstrap: dasync --version and dasync describe --json. It advertises machine protocol versions, command input/output schemas, side-effect classes, required target fields, approval categories and result/diagnostic schemas. An unsupported protocol request fails before configuration reads/writes or prompts.
  • One promised JSON envelope on stdout. Human progress uses stderr; optional event streaming is explicitly negotiated and schema-versioned.
  • Strict no-input mode: no TUI, credential prompt, guessed target, implicit trust, context approval, or overwrite permission.
  • Command schemas come from the authoritative operation definitions; help, machine description, operator brief and tests cannot drift into independent contracts.
  • Engine-owned diagnostics/risk classifications are separate from provenance-tagged recipe prose. JSON serialization does not make source descriptions authoritative.
  • Remediation uses validated structured requests/argv arrays; never execute shell strings from metadata or treat a suggested approval as existing authority.
  • Bounded search/status/summary with pagination and explicit detail/read operations. No requirement to ingest all recipe bodies before choosing an item.
  • Inspection explains intent, dependencies and blockers even when drift or a missing grant prevents a complete render plan.
  • A scope token and plan hash bind target/concurrency inputs. They are not authenticated proof of human permission.
  • Apply returns actual receipt/effects and postconditions. Repeated identical sync is idempotent; stale plans get a replan request rather than blind write retry.
  • Operator handoff/resumption includes pinned references, allowed actions and unknowns, rechecked against current authority; no assumption that a child inherits its parent's access.
The agent operating brief should teach the complete minimum journey: describe → inspect → explicit prepare if required → select/bind draft → plan → inspect risks/effects → apply exact plan → doctor → report actual evidence. It should link to richer command schemas, not embed a long permanent prompt into every provider instruction file.
17Local creation, preview, promotion, and forks
Local creation must not require a Git repository or a recipe repository. A standalone item folder uses an item.yaml envelope containing a durable source UUID, imports, and the same ItemSpec used inside recipes. The internal source snapshot treats it as a singleton; the product surface calls it a local item.
A scaffold command creates the smallest valid item of the requested kind, its content entrypoint, and explicit metadata. It does not invent personal facts, choose a public license for private content, initialize remote accounts, or execute native files. Registering it assigns a readable alias; moving a folder requires a reviewed locator rebind while preserving its source UUID.
Local directory installs use explicitly accepted snapshots. Editing source bytes invalidates reviewed plans. Preview works on current tree bytes in a disposable home/project, clearly distinct from committed Git snapshots. A watch mode may recompute previews; it must not repeatedly apply to real provider roots.
Promotion into a shared recipe changes tuple identity. The export/import workflow produces an explicit old→new item mapping, shows affected selected roots, declared typed references, context slots/bindings and authority, and keeps the old source until the new transaction succeeds. It updates only authorized authored fields; no general prose rewrite or automatic trust/grant transfer. Fork scaffolding regenerates source UUID and rewrites declared self references, preserving licenses and provenance.
Author journey: create recipe/item → edit canonical content → offline validate → disposable provider preview → installed doctor/idempotent sync → PR review → release preparation. Native-file import is an explicit conversion tool with diagnostics and manual gaps. The runtime never supports two competing source formats or executes imported hooks during conversion.
